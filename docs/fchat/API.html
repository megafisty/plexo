F-List API

F-List offers a few basic services for developers who are interested in integrating with the service in various forms. The primary purpose of the API is to export information for use in a third-party chat client.

While using the API, all requests must be transferred over HTTPS. All requests must provide all request fields through a POST urlencoded body, or POST form data encoding. A valid content-type must be provided with all requests. GET requests and URL query strings are invalid. Any reasonable HTTP request library will be capable of providing this for you.

All API responses include an error field, which is an empty string when no error has happened, or a string describing the error that took place.

Examples have the error field stripped from their output to emphasize that it is not part of the content produced by the endpoint.
Boolean input values are often tested against empty strings or the string variants of true/false. Refer to notes on each endpoint that accepts booleans for more information. The return type of booleans is also often expressed through strings. The return format documentation will specify if this takes place.

Unless noted, all API endpoints require authentication. You provide authentication to endpoints as the properties account and ticket. Both properties are required.

These two fields are omitted from the documentation about the request format to help prevent duplicate information.

All examples are done using the wonderful Python requests library.

Authentication

F-List uses a slightly archaic API authentication method that involves submitting login details and being issued a temporary API ticket that is used to access all remaining resources.

Issued API tickets are valid for a duration of 30 minutes, or until a new API ticket is issued for the account. For this reason, interleaved requests between clients are highly error prone without API ticket sharing.

Get API Ticket

Obtains an API ticket for use in future requests. This endpoint also doubles for obtaining various information that is useful during the course of a login screen for a chat client.

Request Properties

Characters

F-List provides an interface for gathering information about characters that use the service. An account and API ticket are required to access all endpoints that request information about a character. Most, but not all character related endpoints now allow for specifying either a name or a character id when requesting information. Only an id or a name should be provided, not both for any given property. If required, you can mix and match ids and names between properties if available.

Character information for characters that have been blocked for administrative purposes, are timed out, or banned, is not accessible and will return an error.

Returns information required to map character fields to display values, such as kinks, infotags, and infotag list values.

  • Destination character not found.
  • Source character not found.

Send Friend Request

Issues a friend request between two characters. The endpoint can fail in the following circumstances:

  • Target character not found.
  • Source character not found.
  • Source character does not belong to you.
  • Cannot friend yourself.
  • This user has blocked you. You cannot friend them.
  • You have a pending friend request already.
  • You have a pending friend request from this character. Please accept it instead of sending an invite.
  • You are already friends.

Chat Reports

Submit Chat Report

Submits the logging evidence for a chat report.

This endpoint does not automatically issue a staff alert within chat when used. Your client must still issue a SFC command after submitting a log.

Chat reports are used as one form of evidence for corroborating that a reportable offense took place. Clients should submit raw logs from the session to this endpoint. It is suggested that clients clip the most recent 2000 messages, 1 hour of channel messages, or 24 hours of private messages. Clients should make a best effort to ensure that logs submitted are not altered by the user before submission.

Submitting logs that contain HTML is deprecated. Your report format should be a text based format without markup. Do not escape HTML entities. Chat report bodies should include a textual header that indicates the client name, version, the current conversation tab name, and a note of any timezone offsets applied to the logs. If the report is a channel the id and title for the channel should be part of the header.
Please notify a moderator or developer before you test this endpoint during development.

Request Format

reportUser String Name of the character being reported for the infraction.
reportText String (Required) A brief summary the user entered about the incident and why they are reporting the incident. Limited to 1500 characters.
log String (Required) The contents of the reported log text, including report header.
text String (Required) Must be set to the string value true .

Chat Login - IDN

Begins the identification process with the chat server.

Clients must provide a client name and version number with all identification requests. Much like the user agent in a HTTP request, these values should reflect the name of the client, and the current version number.

No other commands can be issued until identification has completed successfully.

This command can fail in many ways:

  • IDENT_FAILED - The login details, or ticket were not valid. Clients should not attempt to use the same ticket again.
  • TOO_MANY_FROM_IP - There are too many connections from the current IP address. No reconnection should take place.
  • BANNED_FROM_SERVER - The user is banned from the server. No reconnection should take place.
  • LOGGED_IN_AGAIN - The active connection is being terminated because another one is replacing it. No reconnection should take place.
  • UNKNOWN_AUTH_METHOD - You didn't use the ticket login method. Do not attempt to reconnect automatically.
  • NO_LOGIN_SLOTS - The chat login system is currently too busy to process additional login requests. A staggered and delayed reconnection should take place.
  • SERVER_FULL - The chat server is currently full. No automatic reconnection should take place.
  • ALREADY_IDENT - The connection is already identified and no further identification is required, or you have already issued an identification request and it has not yet completed.
All identification failures are fatal. The connection must be closed and opened again before attempting to identify again.

Protocol Pitfall Advisories

Potential error situations within the F-Chat Protocol, and best practice responses.

All clients, including bots should be able to handle these error situations before connecting to the primary chat server.

Establishing a system for reading a series of protocol commands from an arbitrary input mechanism(file/pipe/input field) is recommended in order to assist in testing clients. This allows for feeding a client a test scenario under isolation without requiring a network connection.

Unknown protocol command

Clients should be capable of handling the case where an unknown or invalid protocol command is issued from the server. Unknown commands are usually an indicator of a protocol update or client bug. Malformed commands are usually an indicator of data corruption, and all further input may be invalid as a result.

Best Practice

For the case of a well formed command with an unknown identifier, the client should discard the command without further processing. Clients may optionally log the information or emit a warning to the user that a command was not properly handled. For the case of a malformed protocol command, where either the identifier or the payload are not well formed, the client may choose to discard the protocol command, or disconnect.

Example

  • XYZ {"data": "foo", "bar": "foo"}
  • A{prop: field}

Unknown protocol command properties

Clients should be capable of handling the case where the server sends a valid protocol command with an unknown property contained within it. Unknown protocol properties are indicators of protocol updates or a client bug.

Best Practice

Clients should only process properties that are known to them, ignoring unknown properties. Clients may optionally log the presence of an unknown property.

Example

  • LCH {"channel": "Development", "character": "Character Name", "flubber": 5.0}

Protocol command property of the wrong type

Clients should be capable of handling the case where the server sends a valid protocol command with a property of a type that does not match the expected type.

Best Practice

Best practice is for clients to disconnect in this situation, as it is an indicator that an incompatible protocol update has taken place, or a major client bug. No automatic reconnect should take place following this disconnection.

Example

  • LCH {"channel": 53, "character": 15}

Protocol command property of unexpected value

Client should be capable of handling the case where the server sends a valid protocol command with a property that contains an unexpected type. Unexpected values are usually an indicator of a protocol update or bad expectations for the strict validity of a field.

Best Practice

Best practice is to use a safe default value for unexpected or unhandled cases, such as when the property is expected to be an enumerator.

Example

  • NLN {"status": "online", "gender": "cake", "identity": "A Character"}

Server closes connection after issuing an ERR protocol command

Clients must maintain a list of error conditions for which an automatic reconnection should not take place. The server closing the connection immediately after an ERR command is a strong indicator that the client or user has encountered a situation where the server is no longer willing to handle the client connection.

Failure to abide by these conditions may result in administrative intervention.

Best Practice

Clients must process the ERR command and inspect the code value and compare it against conditions where reconnection would result in failure. The list of current cases where the client should not attempt reconnection are as follows:

  • 2: The server is full and not able to accept additional connections at this time.
  • 9: The user is banned.
  • 30: The user is already connecting from too many clients at this time.
  • 31: The character is logging in from another location and this connection is being terminated.
  • 33: Invalid authentication method used.
  • 39: The user is being timed out from the server.
  • 40: The user is being kicked from the server.

Example

  • ERR {"code": 40, "message": "You have been kicked from chat."}

Messages from an unknown character

Clients must be able to handle the condition of receiving a message from, or about a character that they are not aware of. There are several potential causes for this problem, however, desynchonization is the primary cause.

Best Practice

Best practice is to handle the case of missing information by defining a default set of properties for characters when they are not known.

Example

  • PRI {"character": "Unknown Name", "message": "Hi there ;>", "recipient": "you"}

Messages from an unknown channel

Clients should be able to handle the situation where they receive messages from a channel they do not currently know about, or believe they are not participating in. Clients should ignore the message without displaying it.

As an exception to this practice, clients should not discard join channel messages for channels they are not participating in, where the character matches the current active character. See the section related to unsolicited channel joins.

Best Practice

Best practice is to issue a single leave channel command per channel if the client believes it is not participating in the channel in question. This signals to the server that the client no longer wishes to receive messages related to the channel. An appropriate LCH message or ERR may be issued by the server depending on the currently channel join state.

Example

  • MSG {"channel": "Development", "character": "A Character", "message": "How do I..."}

Unsolicited channel join

Clients should be able to handle the case where they receive a protocol command where the active character is joining an unknown channel. The server reserves the right to forcefully join a character to a channel, and clients must honor this by updating corresponding state or UI elements appropriately.

Best Practice

Best practice is to treat these unsolicited join commands as user initiated and open channel UI elements according to normal channel joining behavior.

Example

  • JCH {"channel": "ADH-abc", "character": {"identity": "Your Character"}, "title": "Secret Channel"}

Duplicated state updates

Clients should be able to handle the situation where they receive a duplicate state update, such as online notification or channel join message. The primary cause of these types of messages is when the chat system experiences high message send delays, such as during networking problems. The chat employs a queue of protocol messages per connection, and when this queue reaches a maximum size, additional messages are trail dropped until the size falls below the maximum. This results in a dsynchronization of state between server and clients, and to the client, appears as out of order protocol commands, dropped messages, and generally "impossible" scenarios of commands.

Best practice

Best practice is to reconcile the state as best as possible without interfering with client operation. The client should NOT automatically disconnect in order to reconcile state, as this can exacerbate existing desynchronization.

Examples of this situation are as follows:

  • A character joins/leaves a channel twice.
  • A character comes online/goes offline twice.

Other Considerations

The following situation is not strictly an error, but it is one that client authors should be aware of when they are developing clients.

High rate messages and synchronization

Clients should be capable of handling protocol commands related to a single entity such as a character or channel even if they arrive at a high rate. Proper internal synchronization should take place to ensure that potentially concurrent access to mutate a shared object does not result in corruption.

Examples

  • Proper synchronization around file access related to logging for characters and channels.
  • Proper synchronization around updates to shared state for characters and channels.
